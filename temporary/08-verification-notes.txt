#       prisma.mechaClubApplication):
#       WHY: In Prisma, the camelCase client accessor is AUTO-GENERATED

#       but never mentions that `npx prisma generate` will then produce
#       `prisma.aboutEeeClub` / `prisma.eeeClubApplication`. Every one
#       of the ~9 existing call sites would fail to compile. Listed all
#       call sites (identity.ts, both admin-actions, both admin pages,
#       both API routes).

#  A3 — GENERATED TS TYPE IMPORT (import type { AboutMechaClub }):
#       WHY: The generated model TYPE is also renamed by Prisma. The
#       admin form imports `AboutMechaClub` from '@prisma/client' and
#       uses it in a prop type — a hard TS error after the rename.
#
#  A4 — ZOD VALIDATION SCHEMA NAMES (src/lib/validation.ts):
#       WHY: Original Step 4l changed only a COMMENT (line ~1056). The
#       actual exported Zod identifiers (aboutMechaClubUpdateSchema,
#       mechaClubApplicationCreateSchema, mechaClubApplicationStatusEnum,
#       mechaClubApplicationStatusUpdateSchema, mechaClubSemesterEnum)
#       were never listed, nor were the imports of them in 3 files.
#       These are code, not just naming cosmetics — imports break if the
#       exports are renamed and vice-versa. (Renaming the schemas is
#       OPTIONAL for compilation, but recommended for consistency; the
#       instruction notes both the definition and its import sites so
#       they stay in sync whichever way the implementer chooses.)
#
#  A5 — EXPORTED ACTION / COMPONENT / PAGE FUNCTION IDENTIFIERS:
#       WHY: Function/component names like updateAboutMechaClubAction,
#       deleteMechaClubApplicationAction, AboutMechaClubForm,
